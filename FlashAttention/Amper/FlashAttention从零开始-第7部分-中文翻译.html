Flash Attention from Scratch Part 7: A100 Profiling

Flash Attention from Scratch Part 7: A100 Profiling

Nov 01, 2025

本文为由 AI 辅助翻译的中文版，原文见 lubits.ch/flash。为保持准确，技术术语（如 fragment、warp、bank conflict、swizzling 等）保留英文原文。

在第 6 部分中，我们通过 FP 指令融合和 auto-tuning 在 RTX 3090 上超越了参考性能，达到 101.5%。但当我们把同一个 kernel 放到 A100 上运行时，性能掉到了只有 80.3%——从成功到明显落后，差了 20 个百分点。

是什么造成了这两块 Ampere 世代 GPU 之间如此大的性能差距？

在 A100 上 Profiling Kernel 7

让我们对比参考 kernel 与 kernel 7 最优配置的 Nsight Compute profiling 指标。我们将考察三个关键方面：计算流水线利用率、指令数量，以及 A100 的吞吐量特性如何放大我们的指令开销。

这些 profile 是在seq_len=4096, d_head=128下完成的。

计算流水线利用率

我们先来看流水线利用率1——分别看 tensor、FMA（主要是浮点）和 ALU（主要是整数）流水线。数字立刻暴露了一个问题：我们的 tensor 流水线在 kernel 执行期间只有 60.5% 的时间活跃，而参考实现是 75.4%。与此同时，我们的标量流水线明显更活跃：

  • FMA: 29.2% vs 20.5%
  • ALU: 21.2% vs 13.1%
  • 合计高出 50%（50.4% vs 33.6%）

周期数揭示了更严峻的事实。虽然两个 kernel 执行的 tensor 流水线周期数大致相同，但 kernel 7 的标量流水线（FMA 和 ALU）各自的运行时长都相当于参考 kernel 中两者之和。我们做着同样多的矩阵乘法工作，却在标量操作上花了多得多的时间。

RTX 3090：另一番景象

RTX 3090 呢？画面完全不同。Kernel 7 的 tensor 利用率实际上比参考实现略高（48.0% vs 47.2%）。标量流水线活跃度呈现出与 A100 类似的模式——合计高出 53%（14.2% vs 9.27%）——但影响要轻微得多。

消费级 CUDA GPU 的 Tensor 吞吐量

BF16/FP16 输入、FP32 输出2的矩阵乘法吞吐量在消费级 GPU 上被人为限制在半速（相对于 Quadro/Pro 专业卡系列）。因此"有效"的流水线利用率可能接近报告值的两倍——kernel 7 为 95.9%，参考实现为 94.5%。

按有效值来看，tensor 流水线已接近其吞吐量上限。这引出一个关键问题：为什么我们 kernel 的 tensor 利用率在 A100 上显著低于参考 kernel，在 RTX 3090 上却更高（都是与各自的参考 kernel 相比）？

标量指令开销

tensor 流水线利用率为我们指出了问题方向，但还需要深挖。为什么 FMA 和 ALU 流水线如此活跃？让我们对比我们的 kernel 与参考实现的实际指令数量，量化这个开销。

Block 配置

虽然我们性能最好的配置使用，但这里我们展示配置，以便与参考 kernel 做更公平的指令数对比。指令开销的模式在不同配置间是相似的。

我们的 kernel 执行了明显更多的这类指令：

  • IMAD：整数乘加
  • LOP3.LUT：3 操作数的按位逻辑运算
  • MOV：寄存器复制
  • SHF：位移

图中没有展示的是CS2R，它复制特殊寄存器，比如零寄存器RZ。参考 kernel 一条都不执行，而我们的会——这是另一个开销来源，我们将在第 8 部分中消除它。

指令修饰符

这些原始指令数量只说明了一部分问题。像IMAD这样的指令通过修饰符可以服务于多种目的。例如，IMAD的变体包括：

  • IMAD.MOV.U32（寄存器复制）
  • IMAD.SHL.U32（左移）
  • IMAD.IADD（整数加法）

类似地，LOP3.LUT通过查找表（文档）可以实现任意 3 输入布尔运算。

Profiling 带修饰符的指令

Nsight Compute 默认显示基础 opcode（如IMAD）的指令数量，不带修饰符。一个很高的IMAD计数可能大部分是IMAD.MOV.U32操作而不是真正的乘法——这是完全不同的性能图景。

要 profiling带修饰符的指令，请使用sass__inst_executed_per_opcode_with_modifier_all指标，它能细致地展示 GPU 把时间花在了哪里。默认指标sass__inst_executed_per_opcode会把每个基础 opcode 的所有变体聚合在一起。

看修饰符细分才能发现真正的问题。绝大多数IMAD指令实际上是寄存器复制（IMAD.MOV.U32）或左移（IMAD.SHL.U32），而不是整数乘加。这些操作只增加开销，对实际的 GEMM 计算没有贡献。

与参考 kernel 相比，我们执行的：

  • 11.6x倍的寄存器复制（IMAD.MOV.U32 + MOV)
  • 216x倍的逻辑运算（LOP3.LUT)
  • 23.8x倍的左移指令（IMAD.SHL.U32 + SHF.L.U32)

合计起来，大约相当于2 倍的标量指令和总量多 38.7% 的指令。

数据依赖指令

额外指令的数量之多已经令人担忧，但这还不是全部。关键问题在于：许多标量指令会造成数据依赖，阻塞那些真正重要的操作：cp.async, ldmatrix, and mma.

为了量化这一点，我们来统计 main loop 中为cp.async, ldmatrix, and mma计算所用值的独立标量指令数量。这些是写后读（RAW）冒险——一条指令必须等待另一条指令完成后才能读取所需的寄存器值。

这些依赖指令中的每一条都必须先完成，依赖它的内存或 tensor 操作才能开始。它们给关键路径增加延迟、消耗寄存器资源，造成的 stall 让我们无法让 Tensor Core 保持满载。这就是我们的 Tensor Core 在 kernel 执行的大部分时间里闲置的原因。

为什么 A100 受影响：吞吐量比值

让我们汇总一下目前的发现：

  • 在 A100 上，我们的 tensor 流水线利用率远低于参考实现；而在 RTX 3090 上略高
  • 在两块设备上，标量流水线利用率（FMA+ALU）都比参考实现高 50%
  • 我们执行的标量指令大约是 2 倍，产生依赖的指令多 6.8-11.3 倍

为什么这种指令开销在 A100 上严重拖垮性能，在 RTX 3090 上却不会？答案在于截然不同的吞吐量特性：

设备mma TFLOPs/s
（16b 输入，32b 累加）		FP32 TFLOPs/smma / FP32 比值
A100311.8419.516x
RTX 30907135.62x

A100 的 tensor 吞吐量是 RTX 3090 的 4.5 倍，但 FP32 吞吐量只有一半。这造成了悬殊的 tensor 与 FP32 吞吐比值：A100 上为 16 倍，RTX 3090 上为 2 倍。

这种失衡的比值放大了我们标量依赖问题的影响。单靠任何一个因素都无法解释性能差距——关键在于它们的相互作用：

A100（16 倍比值）：Tensor Core 处理工作的速度比标量单元准备数据快 16 倍。当标量依赖阻塞 tensor 操作时，高吞吐的 Tensor Core 只能闲置等待。巨大的吞吐量失衡意味着我们无法掩盖这种延迟——根本没有足够的标量计算在并行进行，无法与 tensor 操作重叠。

RTX 3090（2 倍比值）：tensor 和标量吞吐量更加均衡。即使有同样的标量依赖，较低的 tensor 吞吐量给了更多时间来解决它们。标量开销可以部分隐藏在 tensor 操作延迟之下，而更高的 FP32 吞吐量意味着 Tensor Core 等待期间能完成更多有用的工作。

结果是：我们以标量为主的指令组合在 A100 上造成了严重的瓶颈，Tensor Core 大部分时间都在"挨饿"等数据。RTX 3090 更均衡的架构对同样开销的容忍度好得多。

如果想深入了解这一切在硬件层面如何运作，可以查看附录 A——Ampere 微架构。

为什么 RTX 3090 没有这个问题？

两个硬件约束在 RTX 3090 上掩盖了这些问题：

  1. SMEM 限制：RTX 3090 每个 SM 的 100KB SMEM 反正也跑不了（在足够 occupancy 的前提下）
  2. 已经 tensor 受限：tensor 流水线利用率已接近峰值（有效值约 96%），更大的 block 也帮不上多少忙

A100 的 164KB SMEM 支持更大、更高效的配置——但 kernel 7 过多的寄存器使用使其无法利用这些配置。

总结

我们的分析揭示了为什么 kernel 7 在 RTX 3090 上能达到参考性能的 101.5%，在 A100 上却只有 80.3%。

核心问题

标量指令开销：Kernel 7 执行的指令明显多于所需：

  • 2 倍的标量指令（相比参考实现）
  • 多 6.8-11.3 倍的依赖产生指令，阻塞cp.async, ldmatrix, and mma操作
  • 总指令数多 38.7%

这些依赖指令给关键路径增加延迟，造成流水线 stall，使 Tensor Core 无法保持高利用率。

寄存器压力限制了 block 大小：A100 的最优 block 配置会让 kernel 7 每线程 spill 272 字节的寄存器。这些 spill 需要昂贵的内存访问，抵消了大 block 的好处，迫使我们使用更小、更低效的配置。

为什么 RTX 3090 掩盖了这些问题

均衡的吞吐量：两块设备的吞吐量特性截然不同：

  • A100：16 倍mma对 FP32 的比值——标量依赖解决期间 Tensor Core 在挨饿
  • RTX 3090：2 倍比值——标量开销部分隐藏在 tensor 操作延迟之下

硬件约束：RTX 3090 的限制掩盖了问题：

  • 每个 SM 100KB 的 SMEM 反正也无法在足够 occupancy 下运行更大的 block
  • tensor 流水线利用率已接近峰值（有效值约 96%），更大的 block 帮助不大

A100 的优势——4.5 倍的 tensor 吞吐量和更大 block 的支持——暴露了我们 kernel 的低效：由于标量瓶颈，我们无法让 Tensor Core 吃饱；由于寄存器压力，我们又无法利用更大的 block。

接下来

在第 8 部分中，我们将通过 SASS 级分析追查这些额外的寄存器复制、移位和逻辑运算的来源。通过消除指令开销和降低寄存器压力，我们将显著缩小性能差距——在 A100 上达到参考性能的 95.2%，比现在的 80.3% 提升了近 15 个百分点。
