## `mbarrier.test_wait`、`mbarrier.try_wait`

检查 `mbarrier` 对象是否已经完成指定阶段。
## 语法
```ptx
// 不使用 parity
mbarrier.test_wait{.phase_type::primary}{.sem.scope}{.ss}.b64
    waitComplete, [addr], state;

mbarrier.test_wait.phase_type::primary{.sem}{.scope}{.ss}.b64
    waitComplete|reportPredicate {, reportValue}, [addr], state;

// 使用 parity
mbarrier.test_wait.parity{.phase_type}{.sem.scope}{.ss}.b64
    waitComplete, [addr], phaseParity;

mbarrier.test_wait.parity.phase_type::primary{.sem}{.scope}{.ss}.b64
    waitComplete|reportPredicate {, reportValue}, [addr], phaseParity;

// 不使用 parity
mbarrier.try_wait{.phase_type::primary}{.sem.scope}{.ss}.b64
    waitComplete, [addr], state {, timeHint};

mbarrier.try_wait.phase_type::primary{.sem}{.scope}{.ss}.b64
    waitComplete|reportPredicate {, reportValue}, [addr], state {, timeHint};

// 使用 parity
mbarrier.try_wait.parity{.phase_type}{.sem.scope}{.ss}.b64
    waitComplete, [addr], phaseParity {, timeHint};

mbarrier.try_wait.parity.phase_type::primary{.sem}{.scope}{.ss}.b64
    waitComplete|reportPredicate {, reportValue}, [addr], phaseParity {, timeHint};
```

```ptx
.ss         = { .shared{::cta} }
.sem        = { .acquire, .relaxed }
.scope      = { .cta, .cluster }
.phase_type = { .phase_type::primary, .phase_type::conditional }
```

## 描述

`test_wait` 和 `try_wait` 操作用于检查：操作数 `addr` 指定位置上的 `mbarrier` 对象，是否已经完成当前阶段或紧邻的前一个阶段。

`mbarrier.test_wait` 是一条**非阻塞指令**，用于检查阶段是否完成。

`mbarrier.try_wait` 是一条**可能阻塞的指令**，用于检查阶段是否完成。如果阶段尚未完成，执行该指令的线程可能会被挂起。被挂起的线程会在以下情况恢复执行：

- 指定阶段完成；或者
- 在阶段完成之前，达到了由系统决定的时间限制。

可选的 32 位无符号整数操作数 `timeHint` 以纳秒为单位指定时间限制，可用于替代系统默认的时间限制。

`mbarrier.test_wait` 和 `mbarrier.try_wait` 可以通过以下两种方式指定要检查完成状态的实验阶段：

1. 通过 64 位无符号整数操作数 `state` 指定。该值由当前阶段或紧邻的前一个阶段中，对同一个 `mbarrier` 对象执行的 `mbarrier.arrive` 指令返回。
2. 通过 32 位无符号整数操作数 `phaseParity` 指定。该整数的奇偶性表示 `mbarrier` 对象的当前阶段或紧邻的前一个阶段。

这些指令的 `.parity` 变体，检查由 `phaseParity` 操作数的整数奇偶性所指示的阶段是否完成。该奇偶性表示 `mbarrier` 对象的当前阶段或紧邻的前一个阶段：

- 偶数阶段的整数奇偶值为 `0`；
- 奇数阶段的整数奇偶值为 `1`。

注意：使用这些指令的 `.parity` 变体时，需要在 `mbarrier` 对象的整个生命周期内跟踪其阶段。

`test_wait` 和 `try_wait` 操作仅对以下阶段有效：

- **当前尚未完成的阶段**：此时 `waitComplete` 返回 `False`；
- **紧邻的前一个阶段**：此时 `waitComplete` 返回 `True`。

限定符 `.phase_type::*` 指定要检查完成状态的具体阶段。各种组合的语义如下：

- **未指定 `.phase_type::*`**：检查主阶段（primary phase）是否完成。
- **`.phase_type::primary`**：检查主阶段是否完成，并设置 `reportPredicate` 和 `reportValue`。注意，当 `waitComplete` 为 `False` 时，`reportPredicate` 和 `reportValue` 操作数未定义。对于 `.layout::v0`，`reportPredicate` 和 `reportValue` 始终为零。
- **`.phase_type::conditional`**：必须同时指定 `.parity` 限定符。它检查条件阶段（conditional phase）是否完成；条件阶段可以独立于主阶段完成。对于 `.layout::v0`，主阶段和条件阶段会同时完成。

操作数 `reportValue` 的类型必须为 `.b8`。

如果未指定状态空间，则使用通用寻址（Generic Addressing）。如果 `addr` 指定的地址不在 `.shared::cta` 状态空间的地址窗口内，则行为未定义。

操作数 `addr` 支持的寻址模式，如“地址作为操作数（Addresses as Operands）”一节所述。操作数 `addr` 的对齐要求，如“`mbarrier` 对象的大小与对齐”一节所述。

当带有 `.acquire` 限定符的 `mbarrier.test_wait` 或 `mbarrier.try_wait` 操作返回 `True` 时，它们会构成“内存一致性模型”一节所述的获取模式（acquire pattern）。

可选的 `.sem` 限定符指定内存同步效果，具体见“内存一致性模型”一节。如果省略 `.sem` 限定符，则默认使用 `.acquire`。`.relaxed` 限定符不提供任何内存排序语义和可见性保证。

可选的 `.scope` 限定符指定 `mbarrier.test_wait` 和 `mbarrier.try_wait` 指令能够直接同步的线程集合。如果未指定 `.scope` 限定符，则默认为 `.cta`。相比之下，`.shared::<scope>` 表示的是 `mbarrier` 所在的状态空间。

`.sem` 和 `.scope` 限定符必须同时指定。

当具有 acquire 语义的 `mbarrier.test_wait` 或 `mbarrier.try_wait` 返回 `True` 时，对执行该等待操作的线程，以下内存操作顺序成立：

1. 在已完成的阶段中，CTA 内各参与线程在程序顺序上先于具有 release 语义的 `mbarrier.arrive` 所请求的所有内存访问（异步操作除外），均已执行，并对执行等待操作的线程可见。

2. 在已完成的阶段中，CTA 内各参与线程在程序顺序上先于 `cp.async.mbarrier.arrive` 所请求的所有 `cp.async` 操作，均已执行，并对执行等待操作的线程可见。

3. 在已完成的阶段中，CTA 内各参与线程在程序顺序上先于具有 release 语义的 `mbarrier.arrive` 所请求的、使用同一个 `mbarrier` 对象的所有 `cp.async.bulk` 异步操作，均已执行，并对执行等待操作的线程可见。

4. 对于执行等待操作的线程在程序顺序上于 `mbarrier.test_wait` 或 `mbarrier.try_wait` 之后请求的所有内存访问，不得先于其他参与线程在具有 release 语义的 `mbarrier.arrive` 之前执行的内存访问而执行，也不得对这些先前的内存访问可见。

5. 对于线程在程序顺序上于具有 release 语义的 `mbarrier.arrive` 之后、`mbarrier.test_wait` 之前请求的内存访问，不提供顺序和可见性保证。

## PTX ISA 说明

- `mbarrier.test_wait` 在 PTX ISA 7.0 版本中引入。
- `.parity` 修饰符在 PTX ISA 7.1 版本中引入。
- `mbarrier.try_wait` 在 PTX ISA 7.8 版本中引入。
- 在 PTX ISA 7.8 版本中，引入对 `.shared` 的子限定符 `::cta` 的支持。
- 在 PTX ISA 8.0 版本中，引入对 `.scope` 和 `.sem` 限定符的支持。
- 在 PTX ISA 8.6 版本中，引入对 `.relaxed` 限定符的支持。
- 在 PTX ISA 9.3 版本中，引入对 `.phase_type::*` 限定符的支持。
- 在 PTX ISA 9.3 版本中，引入对 `reportPredicate` 和 `reportValue` 操作数的支持。

## 目标 ISA 说明

- `mbarrier.test_wait` 需要 `sm_80` 或更高架构。
- `mbarrier.try_wait` 需要 `sm_90` 或更高架构。
- `.cluster` 作用域需要 `sm_90` 或更高架构。
- `.relaxed` 限定符需要 `sm_90` 或更高架构。
- `reportPredicate`、`reportValue` 操作数以及 `.phase_type::*` 限定符需要 `sm_90` 或更高架构。

## 示例

### 示例 1a：使用 `test_wait` 进行线程同步

```ptx
.reg .b64 %r1;
.shared .b64 shMem;

mbarrier.init.shared.b64 [shMem], N;  // N 个线程参与该 mbarrier
...
mbarrier.arrive.shared.b64 %r1, [shMem]; // N 个线程执行 mbarrier.arrive

// 执行不需要 mbarrier 同步的计算……

waitLoop:
mbarrier.test_wait.phase_type::primary.shared.b64
    complete, [shMem], %r1;
@!complete nanosleep.u32 20;
@!complete bra waitLoop;
```

### 示例 1b：使用 `try_wait` 进行线程同步

```ptx
.reg .b64 %r1;
.shared .b64 shMem;

mbarrier.init.layout::v0.shared.b64 [shMem], N;  // N 个线程参与该 mbarrier
...
mbarrier.arrive.shared.b64 %r1, [shMem]; // N 个线程执行 mbarrier.arrive

// 执行不需要 mbarrier 同步的计算……

waitLoop:
mbarrier.try_wait.phase_type::primary.relaxed.cluster.shared.b64
    complete, [shMem], %r1;
@!complete bra waitLoop;
```

### 示例 2：使用阶段奇偶值进行线程同步

```ptx
.reg .b32 i, parArg;
.reg .b64 %r1;
.shared .b64 shMem;

mov.b32 i, 0;
mbarrier.init.shared.b64 [shMem], N;  // N 个线程参与该 mbarrier
...
loopStart:                            // 每次循环迭代对应一个阶段
    ...
    mbarrier.arrive.shared.b64 %r1, [shMem]; // N 个线程
    ...
    and.b32 parArg, i, 1;
    waitLoop:
    mbarrier.test_wait.parity.shared.b64
        complete, [shMem], parArg;
    @!complete nanosleep.u32 20;
    @!complete bra waitLoop;
    ...
    add.u32 i, i, 1;
    setp.lt.u32 p, i, IterMax;
@p bra loopStart;
```

### 示例 3：等待异步拷贝完成

```ptx
.reg .b64 state;
.shared .b64 shMem2;
.shared .b64 shard1, shard2;
.global .b64 gbl1, gbl2;

mbarrier.init.shared.b64 [shMem2], threadCount;
...
cp.async.ca.shared.global [shard1], [gbl1], 4;
cp.async.cg.shared.global [shard2], [gbl2], 16;

// 不使用 .noinc，会将先前 cp.async 操作产生的 arrive-on 计入
cp.async.mbarrier.arrive.shared.b64 [shMem2];
...
mbarrier.arrive.shared.b64 state, [shMem2];

waitLoop:
mbarrier.test_wait.shared::cta.b64 p, [shMem2], state;
@!p bra waitLoop;
```

### 示例 4：将 CTA0 中的线程与 cluster 中的线程同步

```ptx
.reg .b64 %r1, addr, remAddr;
.shared .b64 shMem;

cvta.shared.u64        addr, shMem;
mapa.u64               remAddr, addr, 0;     // CTA0 的 shMem 实例

// CTA0 中的一个线程执行以下初始化操作
@p0 mbarrier.init.shared::cta.b64 [shMem], N;  // N = cluster 中的线程数

barrier.cluster.arrive;
barrier.cluster.wait;

// 整个 cluster 执行以下 arrive 操作
mbarrier.arrive.release.cluster.b64 _, [remAddr];

// 执行不需要 mbarrier 同步的计算……

// 仅 CTA0 中的线程执行以下等待操作
waitLoop:
mbarrier.try_wait.parity.acquire.cluster.shared::cta.b64
    complete, [shMem], 0;
@!complete bra waitLoop;
```

### 示例 5：使用 `mbarrier.test_wait` 跟踪异步操作的成功状态

```ptx
.reg .b64 %r1;
.shared .b64 shMem;

mbarrier.init.layout::v1.shared::cta.b64 [shMem], N;  // N 个线程参与该 mbarrier
...

// 发起异步操作的计算，并在位于 shMem 的 mbarrier 上指定报告机制
...

waitLoop:
mbarrier.test_wait.phase_type::primary.shared::cta.b64
    complete|reportPred, reportValue, [shMem], %r1;
@!complete nanosleep.u32 20;
@!complete bra waitLoop;

@reportPred bra noSuccess;
// 异步操作成功完成
...

exit;

noSuccess:
// 处理未成功完成的异步操作
// 检查 reportVal 以获取更多详细信息
```

### 示例 6：通过等待条件阶段，跟踪异步操作是否成功完成

```ptx
.reg .b64 %r1;
.reg .b32 parity, timeHint;
.shared .b64 shMem;

mbarrier.init.layout::v1.shared::cta.b64 [shMem], N;  // N 个线程参与该 mbarrier
...

// 发起异步操作的计算，并在位于 shMem 的 mbarrier 上指定报告机制
...

waitLoop:
mbarrier.try_wait.parity.phase_type::conditional.relaxed.cluster.shared::cta.b64
    complete, [shMem], parity, timeHint;
@!complete bra waitLoop;
// 异步操作成功完成
```
