- SIMT：single instruction multiple-threads
- 每个SM最多可以同时跟踪64个线程束（2,048个线程）。
- Blackwell GPU每个SM具有64K个32位寄存器（共256 KB）和每个SM共256 KB的L1缓存/共享内存。其中最多228 KB（227 KB可用）可以配置为每个SM的用户管理共享内存。
- 任何单个线程块最多可以请求227 KB的动态共享内存（CUDA保留了228 KB中的1 KB）。
- Blackwell 每个 SM 有 4 个 Warp Scheduler，每个 Scheduler 每周期最多发射一条指令，因此整个 SM 理论上每周期最多发射 4 条 Warp 指令。不同流水线中的指令仍然可以并行执行。
- SFU使用专用的SFU流水线，独立于主INT32/FP32和加载/存储（LD/ST）流水线运行。（可以做overlap）
- 每个周期最多四个线程束可以取得进展。例如，内存操作可以通过SM共16个加载/存储（LD/ST）流水线流动（每个调度器四个LD/ST流水线）。（1/4sm几个LD/ST?）
- CTA的语义和thread block相同；注意CTA和SM的区别，比如 `__syncthread()__` 是作用在CTA上而不是SM上
- 我们要尽可能保证高占用率，但高占用率必须与每线程资源限制（如寄存器和共享内存）相平衡。将寄存器溢出到较慢的内存可能会产生新的停顿。
- 线程块独立执行，且没有保证的顺序。这允许GPU调度器将它们分发到所有SM，并充分利用硬件并行性。
- 通常选择32的精确倍数的线程块大小。例如，一个256线程的块（8个线程束 = 256 / 32）完全占用每个线程束，而一个33线程的块将需要两个线程束槽位，并且只使用第二个线程束通道的1/32。

- 一个 SM 能同时容纳的 Warp 和 CTA（Thread Block）数量是有限的，因此你设置的 Block Size 会影响 SM 的 Occupancy（占用率）。

$$
 \text{Occupancy}=\frac{\text{SM 上实际驻留的 Warp 数}}{\text{SM 支持的最大驻留 Warp 数}} 
$$

- ### 为什么推荐 256 Threads/Block开始（可以根据内核的寄存器和共享内存需求以及占用率特性向上或向下调整）？
	- 避免 Warp 浪费：Block Size 最好是 32 的倍数，确保每个 Warp 的 32 个 Lane 都有对应线程。
	- 隐藏延迟：256 个线程对应 8 个 Warp，当部分 Warp 等待访存时，Scheduler 可以切换到其他就绪的 Warp。
	- 提高 Occupancy：适当的 Block Size 有利于让 SM 同时驻留足够多的 Warp。
	- 平衡资源：256 不算太大，可以降低单个 CTA 对寄存器、Shared Memory 等资源的需求，从而让更多 CTA 同时驻留。
- Stream 是 CUDA 提供的逻辑任务队列，它保证同一队列内的执行顺序，同时允许不同队列中的任务在条件允许时并发运行。
- 异步＋流能在要跑多个kernel的一些场景中能起到overlap的作用能更加充分的利用cpu
- Blackwell内存层次结构和特性

| 级别             | 范围           | 容量                                                          | 延迟                                                                       | 带宽（近似）           |
| -------------- | ------------ | ----------------------------------------------------------- | ------------------------------------------------------------------------ | ---------------- |
| 寄存器            | 每线程（在SM上）    | 每SM 64K个32位寄存器（每线程最多255个）                                   | 接近寄存器延迟（寄存器读/写是单周期的，基本上免费）                                               | 每SM数十TB/s（寄存器端口） |
| 共享内存和L1缓存      | 每SM          | 228 KB（227 KB可用）共享 + 剩余作为L1/数据缓存                            | ~20-30周期（L1/共享内存基准测试）                                                    | TB/s（无bank冲突）    |
| TMEM           | 每SM          | 每SM 256 KB SRAM专用于张量核心                                      | ~10周期（SM上的专用SRAM）                                                        | TB/s级与张量核心通信     |
| 常量内存缓存         | 每SM          | ~8 KB缓存用于64 KB `__constant__`空间                             | ~1周期（线程束广播）当缓存且线程束中所有线程访问同一地址时，由于常量缓存和广播行为，速度与寄存器一样快。分支或未命中情况会序列化或产生更高延迟 | TB/s级（广播吞吐量）     |
| L2缓存           | GPU范围（所有SM）  | 总共126 MB                                                    | ~200周期                                                                   | 多TB/s聚合          |
| 本地内存           | 每线程（溢出到DRAM） | 接近无限（由全局内存支持）                                               | 数百→1,000周期（类似DRAM）                                                       | ~8 TB/s（HBM带宽）   |
| 全局内存（HBM或DRAM） | 设备范围（片外DRAM） | 每个Blackwell B200 GPU最多180 GB（每个Blackwell B300 GPU最多~288 GB） | 数百→1,000周期（全局内存延迟）                                                       | ~8 TB/s          |
- **常量内存缓存**：对于小型、只读表，Blackwell为每个SM提供约8 KB的常量内存缓存，支持64 KB的`__constant__`空间。当线程束中所有32个线程加载同一地址时，此缓存在单周期内广播该值。分支读取会在线程间序列化。它非常适合共享小型查找表，如旋转位置编码、带线性偏置的注意力（ALiBi）斜率、LayerNorm γ/β向量和嵌入量化比例。这些在每个线程之间共享，无需全局内存流量。
- **TMEM**不是CUDA C++中正常的指针可寻址空间。相反，传输由张量内存加速器（TMA）使用描述符编排。
- Blackwell B200呈现为一个具有统一全局地址空间的单个GPU。然而，它由两个受光刻限制的裸片组成，通过10 TB/s的裸片间互连连接。每个裸片连接到四个HBM3e堆栈，总共八个HBM3e堆栈。从开发人员的角度来看，HBM内存访问在这个组合地址空间中是统一的
- 优化kernel可以首先考虑观察SM占用率，如果占用率很低可以拉高SM占用率，SM占用率太高的情况下内存就成了瓶颈。
- ncu 关注“一个 kernel 为什么慢（单个算子）”，nsys 关注“整个程序为什么慢”（VLLM/SGLang推理的整个过程）。
- 内存限制工作负载的一个著名示例是LLM的"解码"阶段。在解码期间，LLM需要将大量数据（模型权重或参数）从全局HBM内存移动到GPU寄存器和共享内存。
- `__launch_bound__`这种是需要自己调优拿到对应的数据
- 现代GPU上的缓存行是128字节，由四个32字节扇区组成。在非合并情况下，线程束中的每个线程从分散的地址加载。这导致许多独立的内存事务。即使线程束中的线程访问连续地址，如果第一个地址不是128字节对齐的，线程束的请求也将跨越两个128字节缓存行。
- 合并访存做的不好在ncu里体现为`lower Global Memory Load Efficiency`、`higher DRAM sector read counts`、` average sectors per request above 4.0`
