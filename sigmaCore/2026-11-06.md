严格来说，**这份 PPT 没有展示“先跑一大批配置，再根据结果自动淘汰”的剪枝算法**。它的剪枝主要发生在实验设计阶段：先根据推理机制和实验问题，人工选出 12 个有代表性的配置，再把这 12 个配置各跑两种 workload，形成 24 轮正式测试。

也就是说，**24 轮都实际跑完了，不是从 288 轮里剪成 24 轮**。PPT 没有给出完整的候选配置淘汰记录，因此不能声称它使用了 PSO、贝叶斯优化或某种自动剪枝算法。

## 它是怎么剪的

核心方法可以概括为：**不做全排列，围绕几个明确机制，设计少量单变量对照。**

### 1. 按研究问题拆实验，而不是遍历所有参数组合

原实验主要研究四个问题：

| 研究问题               | 保留的对照                | 没做什么                                 |
| ------------------ | -------------------- | ------------------------------------ |
| Graph 是否有用         | TP8 下 Eager／Graph32  | 没在每种并行配置下都重复开关 Graph                 |
| Graph 是否覆盖实际 batch | CP8 下 G8／G32         | 没扫 G1、G2、G4……G64                     |
| Chunk 如何影响 prefill | 4K／16K，辅以 32K 代表配置   | 没逐 1K 扫描 Chunk                       |
| 显存是否跨过 KV 容量门槛     | mem 0.85／0.90        | 没从 0.50 到 0.99 密集扫描                  |
| 并行模式如何影响性能         | 同条件下的 TP／CP、CP／DP 对照 | 没把 TP／CP／DP 与所有 KV、Chunk、Graph 做笛卡尔积 |

这样每个配置都有明确用途，而不是“为了多跑一个配置而跑”。

### 2. 在机制门槛附近选点，而不是均匀扫参数

这是最关键的剪枝逻辑。

#### Graph：选择“覆盖”和“不覆盖”两个点

CP8 的 Graph 对照中：

- 长输入实际活跃 decode 约为 2 条，G8 已经能覆盖。
- 短输入可以有 32 条同时 decode，G8 覆盖不足，G32 才能覆盖。

所以 G8／G32 正好可以检验：

> Graph 参数的收益是否取决于实际 decode batch，而不是 Graph 数值越大越好。

如果扫 G9、G10、G11，对回答这个问题帮助很小。

#### mem-frac：选择容量门槛两侧的点

一条完整长请求需要 132096 个 KV token，3 条需要：

\[
3\times132096=396288
\]

CP8、Chunk 16K 那组：

- mem 0.85：KV 容量 297664，只能驻留 2 条。
- mem 0.90：KV 容量 431872，可以驻留 3 条。

这两个点恰好位于“能否驻留第 3 条请求”的门槛两侧，因此足以解释显存收益来源。

TP8、BF16 那组则形成反面对照：

- mem 0.85：容量 293632。
- mem 0.90：容量 367616。
- 两者都容不下 3 条完整长请求。

因此吞吐几乎不变。**正例和反例共同证明“跨门槛才有效”，比扫十个显存档位更有说服力。**

#### Chunk：用执行次数差异明显的点

128K 输入下：

- Chunk 4K：整批长输入需要 1024 次 prefill。
- Chunk 16K：只需 256 次。

两者执行次数相差 4 倍，能清楚检验“减少 prefill 执行次数是否提高吞吐”。中间再扫 5K、6K、7K，对这个机制问题不是必需的。

### 3. 复用锚点配置，让一组结果服务多个对照

例如 CP8、FP8、Chunk 16K、mem 0.90、G32 这组结果，既可以：

- 与 Chunk 4K 比较，研究 Chunk；
- 与 mem 0.85 比较，研究显存；
- 作为后续 CP／DP 分析的参考。

这样不用为每对实验都重新设计一套完全独立的配置，能减少启动次数，同时保持对照关系清晰。

### 4. 保留两种输入形状，没有按短输入性能全局剪枝

这一点很重要。原实验的 12 个配置都跑了 8K 和 128K，而不是：

> 先跑 8K，删掉表现差的，再跑 128K。

因为如果这样做，就可能提前删掉只在长输入下有优势的配置，无法发现配置排名随 workload 反转。

所以它剪掉的是**无意义的参数组合**，不是根据单一 workload 的跑分剪掉整个配置类别。

## 为什么这样剪枝

主要有四个原因：

1. **节省 GPU 时间**  
   每次换启动配置都涉及模型加载、Graph 捕获、预热和正式测试，长输入测试成本尤其高。

2. **保证结果可解释**  
   单变量对照可以把性能变化与 Graph 命中、prefill 次数、KV 容量和活跃 batch 对应起来。一次改变五个参数，即使吞吐翻倍，也很难知道为什么。

3. **避免非法或错误配置**  
   例如 Graph 捕获范围与实际 batch 不匹配、上下文长度不足、模型不支持某种并行或 KV 精度，这些配置应该在运行前排除。

4. **实验目标是验证机制，不是寻找全局最优**  
   这份 PPT 要证明“配置敏感、收益依赖状态、指标存在权衡”，并没有声称找到了所有负载下的最优配置，因此不需要密集搜索整个参数空间。

## 如果把这套方法做成自动调优 Agent

可以将人工经验形式化为：

1. **硬约束剪枝**：先删除模型不支持、显存必然不足、上下文越界、Graph 不合法的组合。
2. **机制选点**：Graph 按实际 batch 选覆盖边界；mem 按 KV 驻留门槛选点；Chunk 按输入长度和 prefill 次数选代表值。
3. **单变量粗筛**：从合法基线出发，每次只改变一个参数，找出敏感参数。
4. **分 workload 剪枝**：某个配置只能在“同一 workload、同一 SLO、重复测试稳定劣于其他配置”时淘汰，不能用短输入结果替长输入做决定。
5. **最后细搜**：只对少量有希望的区域做 PSO、贝叶斯优化或局部网格搜索。

所以这套实验的本质是：**先用系统机制把搜索空间剪小，再用少量对照验证因果；它不是已经跑完了一个自动调优搜索过程，也不等于找到了全局最优配置。**
